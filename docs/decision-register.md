## 规格冲突、缺口与不可自行决定事项

1. Sprint 0 原文要求“冻结历法、起卦、紫微流派”，但开工前清单又明确这些须由产品负责人确认。本轮按用户指令采用占位与禁用，Sprint 0 只能算“条件完成”，不能宣称规则冻结。
2. “MVP 必须完成紫微摘要”与阶段计划“V1.1 紫微完整排盘”范围不完全一致。需确认 MVP 是外部库基础摘要、内部最小排盘，还是整体延期。
3. 规格要求 UUIDv7，但 PostgreSQL 16 并非所有部署都原生提供 UUIDv7 生成函数。草案要求由应用生成，待平台确认。
4. 所有写操作支持 `Idempotency-Key`，但 PATCH/DELETE 的保存期限、请求指纹、冲突响应和重放语义未定义。
5. RLS 主体传递、owner 管理跨用户数据、viewer 授权表均未完整定义；迁移草案采用最小安全策略，viewer 分享需后续迁移。
6. “立即硬删除”与数据库备份/PITR 的不可变保留存在物理删除时延冲突，需要明确最大消除期限和密钥销毁策略。
7. 关系对象“已同意”只有加密记录字段，没有同意版本、时间、撤回状态与证明类型的规范。
8. K 线公式权重正项合计 0.84、负项 0.16，不是普通加权平均；0–100 映射、截断与 OHLC 生成公式尚未给出。
9. 原型、业愿、中阴规则只有示例和评分框架，没有足够来源依据，不能据此生产 60 个规则或声称传统正统性。
10. 当前模型名与 DeepSeek API 行为会变化，必须在接入 Sprint 实时核对官方配置，不能硬编码。
